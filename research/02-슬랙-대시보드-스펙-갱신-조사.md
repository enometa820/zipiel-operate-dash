### 코드 정합 — 검증 결과

- **확정 1 (1:1 매핑 맞음, 영어 라벨만 버그)**: m번 슬롯의 한국어 라벨은 `STATUS_KO`에서 '지급 대기'로 정확하다(types.ts:50). 그런데 같은 슬롯의 **영어 라벨이 'On Hold'(보류)로 잘못 적혀 있다**(types.ts:32, DB enum 0003:25). 원래 0001 init에서는 올바른 `Payment Pending`이었는데(0001:14), 0003에서 영어 enum을 'On Hold'로 잘못 개명하면서 의미가 어긋났다. `STATUS_PHASE`는 이 슬롯을 'Payment' 페이즈로 매핑하므로(types.ts:163) 한국어·페이즈·effie 정본은 모두 일관되고, **영어 단어 하나만 틀렸다**. effie에는 '보류/On Hold' 개념이 아예 없다 — m은 지급 대기다.
  - **정정 조치**: 영어 라벨을 `Payment Pending`으로 환원한다. 영향 지점 = `lib/types.ts`의 Status 유니온(32)·STATUS_KO 키(50)·STATUSES 배열(69)·STATUS_PHASE 키(163), DB enum `0003:25`(신규 마이그레이션으로 rename), 그리고 ETL `map_status`의 매핑 키(etl:63 'on hold'→'지급 대기' 분기). (작은 열린 항목: effie 실제 시트 드롭다운의 영어 표기가 'Payment Pending'인지 'On Hold'인지는 새 온에어 시트(B) 접근 시 최종 확인 권장. 한국어 의미는 확정이다.)

- **확정 2 (Drop 자동 규칙 미구현)**: b번의 '제품 발송 후 1개월 이상 무회신·업로드 지연 시 자동 드랍' 규칙은 **코드 어디에도 구현되어 있지 않다**(검증 confirmed). 현재 Drop은 오직 시트 라벨 또는 사람이 수동 지정해야만 생긴다(app/actions.ts는 수동 지정, etl `map_status`는 '드랍/drop' 텍스트 라벨 매핑일 뿐). 시간 경과를 계산해 Drop으로 전환하는 cron·트리거·서버 로직이 0건이다. (참고: queries.ts:227 `STUCK_DAYS=14`는 '정체' 표시용 배지일 뿐 Drop 전환이 아니다 — effie의 1개월 무회신 규칙과 무관.)

- **확정 3 (완료 기준 유형 분기 미반영)**: o번의 '완료 기준이 gifted=업로드 / paid=실지급'이라는 분기가 현재 KPI 게이트에 반영되어 있지 않다. 이는 3절 재무 게이트와 직접 연결된다.

## 3. 재무·비용·물류 모델

effie의 06-26 비용 메시지(코퍼스 13·14행)는 현재 모델과 여러 군데에서 충돌·미충족이다. 핵심은 **단일 KRW 정수 컬럼 하나로는 effie의 다통화·채널분배·세후 실지급 규칙을 담을 수 없다**는 점이다.

### 3-1. 크리에이터 비용

**(a) 집계 게이트 — 협업 완료 + 링크 보유 계정만** (P0, confirmed)
effie: "상태가 협업 완료, 링크가 있는 계정에 한해서 비용 가져와야"(14행). 즉 확정 비용 합산 대상은 `status = Completed AND post_url 존재`로 한정된다.
- 현재 코드 `fetchOverviewStats`의 executedFee 게이트는 `campaignType==='Paid' && DONE_STATUSES.has(status)`인데, `DONE_STATUSES = {'Content Uploaded','Completed'}`라서(queries.ts:226,321) **Completed가 아닌 'Content Uploaded'까지 포함하고, 링크 보유 여부는 검사하지 않는다**. → 실집행 비용이 과대 집계됨.
- 조치: 게이트를 `status==='Completed' && hasPostUrl`로 좁힌다. `CollabFact.hasPostUrl`이 이미 있으니 재사용(queries.ts:111). '확정 비용' KPI와 '제안 파이프라인 가치(pipelineValue)'를 이 게이트로 명확히 분리.

**(b) 통화 별도 선택 — 다통화 저장** (P0, confirmed)
effie: "300,000krw, 200usd 등 통화단위랑 같이 기재 / 통화단위는 별도로 선택하게"(14행).
- 현재 `collaborations.content_fee_krw`는 bigint(KRW 단일 가정), 통화 컬럼이 없다. ETL은 비KRW 통화(TW/HK/US Rate)를 `fee_source='unverified'`로 격리해 합산에서 제외한다(etl:197-207, 0005). 즉 **KRW 외 통화는 사실상 데이터 손실**이다. payments에는 `currency`·`fx_rate`가 있으나(0001:109-110) 협업 입력 단계에는 없다.
- 조치: `collaborations`에 `fee_amount numeric(14,2)` + `fee_currency enum(KRW/USD/JPY/TWD/CNY/SGD/HKD/MYR)` 추가. 표시는 원통화, KPI 합산은 fx_rate로 KRW 환산. 기존 `content_fee_krw`는 환산 캐시로 유지하거나 뷰로 대체. `fee_source` 게이트는 '환율 확정 여부'로 재정의 가능.

**(c) 채널 N분배 — 계약가 / 업로드 채널수, 소수점 둘째 반올림** (P0, confirmed)
effie: "10만원 계약건에 업로드 채널이 3개인 경우, 1/3을 해서 비용을 기재, 소수점 둘째자리까지 반올림"(14행). 예: 100,000 / 3 = 33,333.33.
- 분배 개념·채널수 컬럼이 모델에 전혀 없고, `content_fee_krw`가 bigint라 33,333.33 같은 소수를 담지 못한다.
- 조치: 금액 타입을 `numeric(14,2)`로. 한 협업이 다채널 업로드면 **content_pieces를 채널당 1행으로 적재**하고 `content_pieces.allocated_fee = round(fee_amount / 채널수, 2)`로 분배 저장하는 편이 자연스럽다(4절의 1협업 N콘텐츠 모델과 일치). 콘텐츠당/채널당 단가는 CPV·국가x제품 단가 분석의 기준값이 된다.

**(d) 계약가 대 실지급가 분리** (P1, partially)
effie: "금액은 계약서 내 금액 작성, 실지급액은 재무회계에서 2차 확인"(14행). 또 m항: CPV 산정용으로 매니저가 가단가 300,000으로 작성 → 실지급액은 정연이 하나씩 수기 갱신.
- 2테이블 분리 구조는 이미 있다(계약가 = collaborations, 실지급 = payments.gross/tax/net, 0001:105-117). 다만 payments는 현재 0행이고, '계약가 → 실지급가' 대조 뷰·UI가 없다.
- 조치: Deal Page에 '계약가(매니저, 원통화)' 대 '실지급가(재무, net_krw)' 2행 병기 + 차액 사유(원천징수·환율·채널분배) 표기. payments 미기록 시 '재무 2차확인 대기' 명시(현 `executedFromPayments` 플래그 활용).

**(e) CPV 산정 + 외국인 세금 분기** (P1, confirmed 구조)
effie: CPV = 평균 6개 게시물 조회수당 비용. 가단가(300,000)로 먼저 계산하고 실지급액으로 추후 갱신(m-i·ii). 세후 예 290,100(3.3%)은 **한국 거주 케이스에만** 해당.
- 구조 충족: `collaborations.cpv`(0001:57)·`creators.avg_views`(0001:33) 존재. payments에 `tax_type` 4분기(kr_resident_3.3 / nonresident_domestic / nonresident_overseas / none)와 withholding_rate가 이미 있다(0001:111-112). app/actions.ts의 `WITHHOLDING_RATE`도 kr_resident=3.3, nonresident_overseas=0, none=0으로 분기.
- 즉 **외국인 일괄 3.3%가 아니라 거주지별 분기가 준비되어 있다**(검증 confirmed). effie의 3.3% 예시를 전 외국인에 일괄 적용하지 않도록 CLAUDE.md 규칙·조사 §8 유지. 미충족 = CPV의 '가단가(300k) → 실지급 수기 갱신' 2단계 라이프사이클이 UI에 없음.

### 6-2. [GM1] 2026 인플루언서 관리 시트 — 티어·협업유형·콘텐츠 컨셉 기준

'참고 예시 샘플'로 공유된 글로벌마케팅1파트 통합 시트 발췌. 우리 enum 정본과 대조하면 **실제 차이**가 드러난다.

**(a) 크리에이터 티어 (틱톡 기준) — 우리 `TIER_META`와 다름:**

| 티어 | GM1·위마케팅(틱톡) | 우리 코드(lib/types.ts TIER_META) |
|---|---|---|
| Mega | 100만 ↑ | 1M+ (동일) |
| Macro | 50만 ↑ | 500K–1M (동일) |
| Mid | 20만 ↑ | 100K–500K (**임계 다름**) |

| Reviewer | (위마케팅) 10K 미만 | (없음) |

**(b) 협업 유형 (틱톡 기준) — 우리 `CampaignType`(Gifted/Paid/Affiliate)보다 세분:**
- **유가_main**: 비용 $1,000 이상(2차 미포함), $5,000 이상은 섭외목적 등 상세 기입
- **유가_sub**: 비용 $1,000 미만(소액이라도 나가면 무조건 포함)
- **바터딜**: 제품 제공 조건으로 업로드 약속 / 비용 없음
- **시딩**: 단순 선물 · 업로드 미보장 / 비용 없음

→ 우리 deal_type을 `paid_main / paid_sub / barter / seeding (+affiliate)`로 세분하면 effie의 유가/무가·"단순시딩(n 상태)"·재무 게이트와 더 정확히 맞는다. (매핑: Paid=유가_main+sub, Gifted=바터딜+시딩, 우리 'Simple Seeding/PR' 상태=시딩.) 재무 게이트($1,000 임계·소액 포함 규칙)도 이 분류 위에서 자연스럽다.

**(c) 콘텐츠 컨셉 택소노미** (가이드라인): social proof(celeb/viral/dupe) · edu(how-to/ingre/science/proof-substitution/rating/routine) · pain point(problem/in a week) · visual(texture/food/packaging) · etc(언박싱 등). → `content_pieces.category`·가이드라인 구조의 표준 분류로 채택 가치(P2).

**(d) 캠페인 유형**: 일반 · **더마**(=derma, research/01의 derma42와 연결) · AF_아마존 · AF_틱톡샵 · 세일즈_코스트코/부츠/타겟/예스스타일. → 캠페인 1차시민화 시 type 분류의 참고(시딩 외 어필리에이트·리테일 세일즈 채널까지 한 분류 체계로).

**도입 우선순위**: 티어 임계 정합(P1, effie 합의 필요) · deal_type 세분(P1, 재무 게이트 정밀화) · 콘텐츠 컨셉/캠페인 유형 분류(P2, 채택 시 가이드라인·캠페인 모델 보강).

# zipiel 시딩 대시보드 — 빌드 계획 v2 (새 스펙 흡수)

> 출처 대조: effie 새 채널 코퍼스(C0BDVHVNBPS, 06-25~26) · 배송 시트 CSV(396행·등기번호 371 unique) · 코드/DB/ETL 직접 Read · research/00·01 · 기존 결정 D-1~D-13. 모든 주장은 실제 파일 대조로 확정했고, 미확정은 (추정)/(가정) 라벨. raw PII·크리덴셜 미포함.
> 한 줄 요약: 기존 "상태 파이프라인 DB"는 그대로 두고, 그 위에 (1번) 캠페인 KPI·역산 레이어와 (2번) 분석/재무/물류 레이어를 얹는다. 가장 먼저 할 일은 새 기능이 아니라 **데이터를 부수지 않는 ETL 전환과 출처 태깅** — 이게 안 되면 새 온에어·배송 데이터를 손실 없이 못 받는다.

## 1. 큰그림 (vision)

현재 대시보드는 "지금 어느 협업이 어느 상태인가"를 보여주는 **운영 파이프라인 대시보드**다(좌측 사이드바 + 상태그룹 시트 그리드 + detail 패널, D-12). effie의 새 스펙은 이걸 부정하지 않는다 — 같은 데이터 위에 두 개의 새 렌즈를 추가로 요구한다. 결과적으로 한 앱이 3개 레이어로 자란다.

**레이어 1번 — 운영 파이프라인 (기존, 유지)**
협업 1건 = DB 1행, 15상태 정본, 상태 한영병기·시트 색(D-13), append-only 상태이력. 시트 파편화·동시편집 충돌을 구조적으로 해소한 부분(research/01 §7.1). **이 레이어는 건드리지 않는다.**

**레이어 2번 — 캠페인 KPI·달성률·역산 (research/01 P0, 아직 비어 있음)**
팀이 매일 실제로 보고하는 단위는 협업 1건이 아니라 **캠페인 = 브랜드 × 국가 × Dedicated/Integrated × 번호**(research/01 §4.4·§7.2). 대표(수영)의 가장 강한 미충족 니즈는 "현황"이 아니라 "역산과 우선순위"(06-25: "역산해서 며칠까지 몇 개를 섭외해야 하는지")다. effie 새 스펙의 "온에어 예상건 vs 실제 온에어 = 달성률"(코퍼스 15행)이 바로 이 레이어의 분자/분모다.

**레이어 3번 — 분석/리포팅·재무 (effie 새 스펙, 신규)**
일/주/월 시계열(콘텐츠 수·캠페인별·국가x티어·국가x제품), 업로드 후 인게이지먼트(%), % 비중, 기간 필터(코퍼스 15·16행) + 재무(통화별 크리에이터 비용·1/N 채널분배·세후 실지급·마케팅비·물류비·제품원가, 코퍼스 13·14행).

**한 앱에 어떻게 자연스럽게 통합되나 (IA 진화).**
현재 3탭(Overview / Work board / 개발현황)에 레이어가 land될 때마다 탭이 자란다:

| 탭 | 레이어 | 상태 |
|---|---|---|
| **Overview** (보는 화면, 대표·effie) | 1+2 | 기존 → 캠페인 KPI 요약·전일 델타 추가 |
| **Campaigns** (신규) | 2 | 캠페인 KPI 보드 + 마감 역산 우선순위 |
| **Work board** (하는 화면) | 1 | 기존 유지 + 출처(active/발굴풀) 필터 |
| **Analytics** (신규) | 3 | 시계열 차트·인게이지먼트·% 비중·기간 필터 |
| **Finance** (신규) | 3 | 비용 4축 롤업(크리에이터비+물류비+COGS+마케팅비)·통화별·계약vs실지급·송장 매칭 |
| Deal Page `/collaborations/[id]` | 1+2+3 | 기존 + 계약가vs실지급·계약서/드라이브 링크·콘텐츠 성과·배송 진척 |
| 개발 현황 `/status` | — | 유지(D-5, 무엇이 채워졌나 투명 공개) |

단순함 원칙: 6탭을 한 번에 만들지 않는다. **Campaigns는 P0, Analytics·Finance는 P1**에 land하며, Finance는 초기엔 Analytics의 한 섹션으로 시작했다가 비용 데이터가 채워지면 독립 탭으로 승격해도 된다(가치가 분리를 정당화할 때).

## 2. 데이터 모델 델타 (DDL 수준)

진실 우선순위: 아래 컬럼은 effie 코퍼스 요구를 직접 충족하기 위한 것이며, 각 변경에 effie 근거를 명시한다. **현 스키마를 부수지 않고 add-column·신규 테이블로만 확장**한다(기존 `content_fee_krw`·`payments`는 유지·재해석).

### 2-1. 상태 EN 라벨 정정 — `On Hold` → `Payment Pending` (정합 버그)
effie m = "지급 대기"(Payment Pending). 0001 enum은 올바른 `Payment Pending`이었는데 **0003에서 `On Hold`로 잘못 개명**됐다. 같은 파일 `STATUS_KO`는 이미 `'On Hold': '지급 대기'`로 매핑(types.ts:50) — EN만 어긋났다. effie 정본엔 "보류" 개념이 없다.

```sql
-- 0006_rename_payment_pending.sql
alter type collab_status rename value 'On Hold' to 'Payment Pending';
```
코드 동반 수정: `lib/types.ts` Status 유니온·STATUS_KO 키·STATUS_PHASE 키·PHASE_STATUSES, `lib/status-style.ts`, `scripts/etl_seeding.py` map_status 라벨. (effie 근거: 코퍼스 6행 m / 검증요청1·2 confirmed)

### 2-2. 출처 태깅 — 손실 없는 참조의 전제 (현재 0 컬럼)
세 데이터 세계(옛 컨택리스트 / 새 온에어 / 배송)가 들어오면 "이 행이 어느 시트·탭·행에서 왔나"를 행에 남겨야 역추적·증분 머지·중복판정이 가능. 현재 코드 전체에 source 컬럼 0건(grep 확인).

```sql
-- 0007_source_tagging.sql
alter table collaborations add column if not exists source_system text; -- legacy_contact_list | onair_2026 | ship_sheet
alter table collaborations add column if not exists source_sheet_id text;
alter table collaborations add column if not exists source_tab     text; -- gid 또는 탭명
alter table collaborations add column if not exists source_row      int;
alter table collaborations add column if not exists external_ref    text; -- 소스 자연키(예: '10ymVk:1526933782:42')
create index on collaborations (source_system);
create unique index if not exists collab_external_ref_uniq
  on collaborations (external_ref) where external_ref is not null; -- 재동기화 멱등

alter table creators add column if not exists source_system  text;
alter table creators add column if not exists in_legacy_list boolean not null default false; -- effie: 기존 리스트업 중복 인원 별도표시·필터
```
(effie 근거: 코퍼스 6행 ii "기존 리스트업과 중복 인원은 포함하되 별도 표시(필터링 가능)" + 14·15행 새 시트 = "우리의 실제 데이터" / reconciliation P0)

### 2-3. 재무 — 다통화 + 1/N 채널분배 + 계약가 vs 실지급가
현재 `content_fee_krw bigint`(KRW 단일, 통화 컬럼 없음) → 비KRW를 `unverified`로 버려 합산 제외(데이터 손실). bigint라 소수(33,333.33) 불가.

```sql
-- 0008_fee_currency_channels.sql
create type fee_currency as enum ('KRW','USD','JPY','TWD','CNY','SGD','HKD','MYR');

alter table collaborations add column if not exists fee_amount   numeric(14,2);  -- 원통화 계약가 정본
alter table collaborations add column if not exists fee_currency fee_currency default 'KRW';
alter table collaborations add column if not exists upload_channel_count int;    -- 업로드 채널 수
alter table collaborations add column if not exists contract_pdf_url text;       -- 계약서 PDF(코퍼스 14행)
-- content_fee_krw 는 KRW 환산 '캐시'로 유지(기존 Overview KPI 호환). 신규 입력 정본 = fee_amount + fee_currency.

-- payments: 계약가↔실지급가 분리(2테이블 구조는 이미 있음 — 의미만 확정)
alter table payments add column if not exists contract_amount   numeric(14,2);   -- 계약서 금액(원통화, 매니저 입력)
alter table payments add column if not exists contract_currency fee_currency;
alter table payments add column if not exists channel_split      numeric(6,3);    -- 1/N 비율
-- gross_krw = 계약가 KRW환산, net_krw = 실지급(세후, 재무 2차). tax_type/withholding_rate 분기 유지.
```
1/N 채널분배는 **콘텐츠 단위(content_pieces)에 배분 적재**하는 게 자연스럽다(아래 2-4): `allocated_fee = round(fee_amount / upload_channel_count, 2)`. KRW 환산은 payments.fx_rate 패턴 재사용(전용 환율 테이블은 가치가 정당화될 때만 — 지금은 상수/일별 환율 캐시로 충분, 추정).
(effie 근거: 코퍼스 14행 "300,000krw·200usd 통화단위 별도 선택 / 채널 3개면 1/3 소수둘째 반올림 / 계약서 금액은 매니저, 실지급은 재무 2차" / finance·reconciliation P0)

### 2-4. content_pieces — 성과·제품·발행일·분배 (스키마는 있으나 ETL이 0건 적재)
모든 시계열·달성률·인게이지먼트가 이 fact 위에서 돈다. 빠진 컬럼 추가. **실제 업로드일(posted_at)은 이미 컬럼이 있으나 비어 있음** — 달성률 분자의 핵심.

```sql
-- 0009_content_metrics.sql
alter table content_pieces add column if not exists reposts            integer;       -- 코퍼스 15행(누락)
alter table content_pieces add column if not exists quotes             integer;       -- 온에어 시트 Quotes(X)
alter table content_pieces add column if not exists product            text;          -- Posted Product → COGS 매칭
alter table content_pieces add column if not exists scheduled_post_date date;          -- 예상 온에어(달성률 분모)
alter table content_pieces add column if not exists allocated_fee      numeric(14,2); -- 1/N 분배 비용
alter table content_pieces add column if not exists platform           platform;      -- 채널(콘텐츠 수=채널 수)
-- saves = '북마크'로 명시 라벨(코퍼스 15행 북마크). likes/comments/views/shares 는 이미 존재.
-- engagement_rate 는 저장 대신 쿼리/뷰 계산(소수·갱신 잦음):
--   (coalesce(likes,0)+comments+shares+saves+reposts) / nullif(views,0)
```
온에어 시트(39컬럼)에 Likes(IG,TR,TT,X,YT)·Comments·Views·Shares·Reposts(TR,X)·Saves(TT,X)·Quotes(X)·Posted Product·Scheduled Post Date·Upload Link·Original Video Link가 모두 있음(컬럼사전 08_On-Air) → 적재 소스 확보됨(접근만 필요).
**설계 제약**: 1협업 N채널 업로드면 content_pieces를 채널당 1행으로 적재 → "콘텐츠 수 = 채널 수"와 1/N 분배가 동시에 자연스럽게 풀린다. (effie 근거: 코퍼스 15행 6지표+인게이지먼트, 14행 1/N / analytics P0)

### 2-6. shipments — 물류비·송장 매칭 (테이블 부재, PII 제외 적재)
배송 CSV 24컬럼 중 **PII(수취인명·전화·우편번호·주소)는 적재하지 않는다.** 매칭은 등기번호(AA#########AA)로만 — 배송 시트엔 handle이 없으니 이름 직접매칭 금지.

```sql
-- 0011_shipments.sql
create table shipments (
  invoice_no      text primary key,           -- 등기번호(371 unique)
  carrier         text,                        -- 정규화: K-Packet/한중해상/EMS/SeaExpress
  request_date    date,                        -- 요청일자
  processed_date  date,                        -- 처리일자
  weight_g        integer,                     -- 총중량(g)
  fee_krw         numeric(12,2),               -- 총요금(송장 dedup 1회 — 제품 다행 반복 주의)
  country_code    text,                        -- CN/JP/TW/HK/SG
  brand_tag       text,                        -- 국가코드 칸의 'H&H' 등 비-국가 태그 분리
  customs_no      text,                        -- 승인번호
  delivery_status text,                         -- 접수/교환국 도착/상대국 인계/배달완료/미배달(희소)
  source_sheet_id text, source_row int,
  match_status    text not null default 'unmatched' -- matched/unmatched(effie '없으면 별도 마크')
);
alter table collaborations add column if not exists invoice_no text references shipments(invoice_no);
-- 송장 다제품(EMS) 분해는 가치가 정당화될 때만(P2): shipment_items(invoice_no FK, product_id FK)
```
배송 CSV 실측: carrier 라벨 난립(K패킷 147·한중해상 119·K-Packet 77·k 패킷 19·k패킷 5·EMS 4·SeaExpress 3 → 정규화 필수), 국가코드 칸에 H&H 혼입, 제품명 칸 시프트 → 제품은 배송시트 말고 온에어 'Posted Product' 기준. 총요금 송장 dedup 합 ≈ **253만원**(2026-04-16~06-25). (effie 근거: 코퍼스 14행 송장 매칭·물류비 / 검증요청7 confirmed)

## 3. 데이터 정합·마이그레이션 실행안 (손실 0 보장)

**가장 중대한 결함 둘(둘 다 P0):** (1번) ETL이 매 실행 `DELETE id=not.is.null` + 0003의 `truncate ... cascade`로 **status_history와 인앱 편집을 파괴**한다. (2번) 출처 태깅 컬럼이 없어 역추적·증분 머지가 불가. 둘 다 effie의 "손실 없이 가져와 쓴다"와 정면충돌.

**실행 순서:**

1번. **옛 14k 보존(frozen import).** 기존 collaborations/creators에 1회 백필 `UPDATE`로 `source_system='legacy_contact_list'`, `in_legacy_list=true` 태깅. **이후 이 행들은 wipe 금지.** 옛것은 "발굴 풀(Sourcing)"로 격하(effie가 코퍼스 6행에서 명시 격하).

2번. **ETL을 DELETE-all → 소스별 upsert로 재설계.** `scripts/etl_seeding.py`를 소스별 함수로 분리:
   - legacy = 1회 frozen import(이미 적재됨, 재실행 시 wipe 안 함).
   - onair = `(handle,platform)[+campaign]` 또는 `external_ref=gid:row`로 `ON CONFLICT DO UPDATE`. **status는 인앱 편집이 더 최신이면 보존**(last_synced 비교 또는 status-merge 규칙) — server action 편집을 덮지 않게.
   - ship = `invoice_no` upsert.
   - **`truncate collaboration_status_history`는 영구 금지.** 0003의 truncate는 일회성 enum swap용이었고, 앞으로의 ETL은 insert/upsert만.

3번. **새 온에어(B) 적재 — 접근 확보가 선행 블로커.** 현재 401(권한 없음). 시트(10ymVk...)를 enometa@theframeless.co 또는 서비스계정에 공유받아 스냅샷 확보(PII gitignore) → upsert. **옛 On-Air 탭 83행과 중복**되므로(추정: 새 온에어 = 옛 On-Air의 진화 후속본), 같은 키로 충돌 시 INSERT가 아니라 legacy 행을 `onair_2026`로 승격·필드 최신화 → 이중계상 방지.

4번. **배송(C) 적재 — 스냅샷 이미 보유(scratchpad CSV).** shipments에 송장 dedup(제품 다행 반복 1회 집계) + carrier·국가코드·H&H 정규화, PII 제외. `collaborations.invoice_no` equi-join 매칭, 실패분 `match_status='unmatched'`('별도 마크'). 타브랜드(H&H 91건)는 매칭 성사분만 zipiel KPI에 귀속.

5번. **필드별 SSOT 정책을 머지 레이어에 코드화.** 상태·fee = onair가 legacy를 덮음(legacy 보존·비활성). 물류 = ship_sheet가 보강. 실지급(net) = 재무 2차(payments). 발굴/티어 베이스라인 = legacy.

**손실 0 보장 메커니즘 요약:** legacy frozen(삭제 금지) + 모든 행 출처 좌표 태깅(역추적) + external_ref 멱등 upsert(재동기화 안전) + status_history append-only·truncate 금지 + 인앱 편집 우선 머지 규칙. **분리축은 status 휴리스틱(현 NOT_SOURCING)이 아니라 `source_system`** — 새 온에어 적재 후 `source_system='onair_2026'`이 곧 active의 정의가 된다(queries.ts:83 교체).

## 7. 첫 스프린트 제안 (우로보로스 spec 후보)

**후보 1번 (최우선·외부 의존 0) — slug: `etl-safe-incremental-logistics`** ★ 권장

- ROI: 위험 제거 + 가시적 가치 동시. 가장 단순한 형태로 가치 전달.

## 8. 레퍼런스 시트 반영 (위마케팅·GM1 실데이터)

effie가 준 두 레퍼런스 시트를 직접 받아 분석한 결과(조사문서 §6), 모델·IA에 반영할 3건:

1. **Analytics 탭 IA = 위마케팅 2존 구조 차용** (P1, §5 보강). Overview(고정 월 + **전월대비** 4블록: 주차별·유형별·유가무가·티어별) + Details(커스텀 기간: 그룹별·담당자별, 각 행 **동기간 대비**). 표준 지표 = 업로드·조회수·평균조회수·저장수·**우수 컨텐츠(품질 임계 카운트)**·배송건수·비용·**잔여 예산**. → content_pieces에 품질 플래그(boolean), campaigns에 budget 소진 뷰 추가 후보. '동기간 대비'는 status_history append-only가 데이터 소스.

2. **deal_type 4분류 세분** (P1, §2-3·2-8 보강). GM1 기준 `paid_main($1,000↑)/paid_sub($1,000↓·소액포함)/barter(제품조건 업로드약속)/seeding(단순선물·업로드 미보장)`. 현재 CampaignType 3종(Gifted/Paid/Affiliate)보다 정밀 → 재무 게이트($1,000 임계)·effie 유가무가·'Simple Seeding/PR' 상태와 정합. campaigns.deal_type 또는 collaborations에 세분 컬럼.

3. **티어 임계 정합 필요** (P1, blocked-effie 합의). GM1·위마케팅은 틱톡 스케일(Mega 100만/Macro 50만/Mid 20만/Micro 20만↓, Nano 없음 / 위마케팅판 Micro 10K↑·Reviewer 10K미만)인데 우리 TIER_META는 일반 스케일(Mid 100K·Micro 10K-100K·Nano 1K-10K). ETL이 시트 Tier 라벨을 그대로 신뢰하므로 임계 정의를 effie와 합의해 명문화(§6 차단 항목에 추가).

> 콘텐츠 컨셉 택소노미(social proof/edu/pain point/visual/etc)·캠페인 유형(일반·더마·AF·세일즈)은 P2 채택 후보(content_pieces.category·캠페인 type 분류 보강).

## 9. 크롤링 통합 (크리에이터 발굴) — 별도 엔진 + DB 적재

> **상태: 백로그 (2026-06-26 파킹)** — 오퍼레이트(운영) 시스템(데이터 토대 → 작업자 작업면 → 대표 대시보드/시각화) 구현 후 착수. 공식 API 하이브리드(발굴=크롤러/Apify, 보강=Business Discovery `source_system='ig_graph_api'`)도 이 백로그에 함께 둠. BP 정본 = `references/bp-anti-bot-scraping-rate-limits.md`.

**결정**: 크롤러 엔진은 **별도 시스템으로 유지**(`C:\Projects\zipiel-instgram` + 글로벌 스킬 `instagram-hashtag-collect`), 대시보드는 그 **결과를 받아 dedup·관리하는 적재/오케스트레이션 면**이 된다. 프로젝트 CLAUDE.md "크리에이터 발굴(크롤링)은 별도 시스템 소관 — 여기서 만들지 않는다"를 유지한다.
- **왜 분리**: 크롤러는 인스타·틱톡이 바뀌면 깨지는 취약한 스크래퍼(쿠키·내부 API·rate limit 대응). 대시보드는 안정적 운영 정본(system of record). 결합하면 플랫폼 깨질 때마다 대시보드가 흔들린다. (BP `bp-ai-native-data-layer`: "툴은 바뀌어도 운영 데이터는 남는다 — 툴부터 고르는 게 안티패턴.")

**통합 지점 = 토대 스프린트의 출처태깅.** 크롤 결과 → `creators`/`collaborations`에 `source_system='crawler'`, `external_ref=(해시태그·플랫폼·username)`, `in_legacy_list` dedup. 이로써 **"새 발굴 vs 이미 컨택함"이 자동 가시화** — effie/대표의 "기존 리스트업과 중복 인원 별도 표시·필터"(코퍼스 6행 ii / research/01 §6 대표 봇 리스트업 커밋) 요구를 대시보드가 충족한다. 크롤러 단독으론 못 하고, 정본 DB라서 가능한 일.

**두 스프린트(토대 다음):**
- **`crawler-result-ingestion`(P1-I)** — zipiel-instgram 출력(`creators_seeding.csv`·워크북 등) → 대시보드 DB 멱등 upsert(`source_system='crawler'` dedup). Work board 출처 필터에 crawler 레인. 외부 의존 = 크롤러 실행(별도)·쿠키 신선도. 토대만 깔리면 작음.
- **`crawl-request-trigger`(P2-M)** — 대시보드에서 해시태그 큐 투입 → `crawl_requests` 테이블 → cron 워커가 rate-safe 페이스로 드레인 → 결과 자동 적재. 대표의 "해시태그만 주면 봇이 리스트업" 완성형.

**rate limit 회피는 구조로 푼다**(임계를 몰라도 안 걸리는 구조): ① 요청을 클릭이 아니라 **스케줄러가 페이싱**(버스트 제거) ② **캐시·재개**(resume — 차단돼도 진행 손실 0, 며칠 분산) ③ **지터 백오프**(고정 간격 회피) ④ **가장 싼 엔드포인트로 배치**(호출 수 최소화, `users/{pk}/info` 등) ⑤ 자체(소량·무료) / **Apify**(대량·안정) 분기. zipiel-instgram이 이미 ①~④의 상당 부분(2초+지터·429/소프트블록 감지·휴식·캐시 재개) 구현. 상세 BP = `~/.claude/skills/enometa-shared/references/bp-anti-bot-scraping-rate-limits.md`(별도 카탈로그 조사).
